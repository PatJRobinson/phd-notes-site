# RQ2 Open Tensions

## Live tensions

- Boundary instability vs boundary construction: avoid claiming boundaries do not exist.
- RQ2 vs RQ4 boundary: recent feedback suggests the distinction may not be visible enough. RQ2 should explain composition, boundary-making, and integration conditions; RQ4 should explain assurance-claim validity under change.
- ROSness: the source note is now promoted as valid for the ROS 2-style robotics thread, but it carries older security-invariant provenance and should be source-audited before public/evidence-heavy use.
- Scenario: useful as a candidate boundary-making construct, but not yet a settled analytic category.
- MOSA: highly relevant to modularity but may pull RQ2 toward broader defence/procurement debates.
- Rotifer: useful for modelling boundaries, but should not become the only evidence source.

## Historical tensions that may still matter

- Layer-misalignment framing treats unstable system definition as the root of security framework weakness.
- Fragmentation framing is strong but needs evidence discipline.

## Superseded tensions

- "What is ROS?" as a static ontology is less useful than "which ROS properties are load-bearing in a given deployment?"

## Decisions needed from me

- Which boundary types should be named: ROS graph, deployment, network, responsibility, evidence, assurance, provider, scenario?
- How much MOSA belongs in the main RQ2 argument?
- How should ROSness be rewritten into a stable concept while preserving enough of the source note's research voice?
- Whether the RQ2/RQ4 distinction needs revised wording or only stronger scope prose.

## Risks if unresolved

- RQ2 may become too abstract.
- RQ2 may be read as duplicating RQ4 if the assurance boundary is not made explicit.
- Boundary language may overclaim instability.
- ROSness material may carry unverified external claims.
