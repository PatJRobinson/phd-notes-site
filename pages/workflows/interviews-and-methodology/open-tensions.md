# Interviews and Methodology Open Tensions

## Method name

The current best label is reflexive, abductive thematic analysis supported by a structured assumption-elicitation protocol. If the protocol becomes a fixed coding frame, the method name may need to change.

## Unit of analysis

"ROS user" is too broad. The study needs a more precise account of whether it is studying integrators, developers, operators, maintainers, security specialists, or teams around integration work.

## Security language

Security should be present analytically, but the interview guide currently avoids direct security framing so participants talk about breakdown, access, responsibility, and trade-offs in ordinary terms. The unresolved decision is how much security language to introduce in recruitment, consent, and debrief material.

## Evidence status

This area of work must continue to distinguish design scaffold from empirical findings. It is acceptable to say the protocol is ready to elicit evidence. It is not acceptable to say the candidate patterns have been found until interviews and analysis exist.

## Assumption and scenario scope

Assumption is useful as a sensitising concept, but it should not absorb requirements, responsibilities, dependencies, omissions, or design decisions without distinction. Scenario is useful as a candidate comparative object, but it may need to split into operating context, configuration, test case, use case, and assurance context after standards analysis.

## Public grounding

The literature notes now provide usable anchors, but many still need exact bibliographic details and source-section extraction before they can carry heavy claims in a thesis chapter.
