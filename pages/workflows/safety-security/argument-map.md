# Safety/Security Argument Map

## Core argument

Safety/security concerns in ROS 2-style robotics often become actionable, fragile, or contested at integration interfaces.

## Supporting arguments

- Security mechanisms depend on correct system-level meaning and configuration.
- Responsibility boundaries are often assumed rather than enforced.
- Visibility determines whether safety/security states can be managed.
- Command authority shows how a physical consequence can depend on graph/interface assumptions.

## Counterpressure

- Avoid broad claims that all safety/security problems are integration problems.
- Avoid treating command authority as representative of all safety/security.
- Avoid turning SROS2 into the centre unless the evidence supports it.
